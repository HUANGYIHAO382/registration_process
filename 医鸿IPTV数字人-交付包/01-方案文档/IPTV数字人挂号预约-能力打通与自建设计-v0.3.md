## 1. 先看清难点：电视挂号难在哪

很多人以为难点是"接 HIS 接口"。不是。真正的三个难点：

| 难点                  | 具体表现                                     | 影响                       |
| ------------------- | ---------------------------------------- | ------------------------ |
| **① 身份认不出来**        | 电视端没有输入法、没有实名信息、没有就诊卡。IPTV 账号只对应宽带，不对应患者 | 不知道"给谁挂号"，这是第一道墙         |
| **② 号源是实时变动的稀缺资源**  | 号源池秒级变化，电视端一次查询+确认可能耗时 60 秒，期间号可能被抢走     | 会出现"说好了却挂不上"的尴尬，老人无法理解   |
| **③ 老人不会操作，必须有人代劳** | 老人说不清科室、记不住身份证号、不会支付                     | 必须支持**子女远程代挂**，否则真实使用率极低 |

> **结论：数字人在这个场景里的价值不是"能挂号"**——公众号、APP 都能挂号。它的价值是 **"能问清楚症状、给对科室、把老人不愿开口的需求问出来"**。挂号只是闭环的最后一公里。
>
> 所以自建能力的重心应该放在**导诊**，对接能力的重心放在**号源与身份**。

## 2. 全链路业务流程（8 步）

```
[1] 触发      数字人主动询问 / 老人按键进入"看病挂号"
      ↓
[2] 身份识别   扫码绑定（首次）→ 后续免认
      ↓
[3] 症状导诊   数字人多轮追问 → 推荐科室（自建核心能力）
      ↓
[4] 号源查询   查医生/日期/时段（走预约中台，带缓存）
      ↓
[5] 确认      复述确认：科室 + 医生 + 时间 + 就诊人
      ↓
[6] 占号下单   预占 → 下单 → 支付（可选，支持到院付）
      ↓
[7] 凭证下发   大字取号码 + 二维码 + 就诊须知
      ↓
[8] 提醒闭环   前一天电视弹窗提醒 + 短信 + 停诊变更通知
```

**每一步的失败都会毁掉体验，尤其第 5 步的"复述确认"和第 8 步的"提醒"——这两步是老人场景的信任来源。**

## 3. 三条实施路径（建议 C 冷启动 → B 为终态）

| 路径             | 做法                           | 依赖             | 工期    | 适用              |
| -------------- | ---------------------------- | -------------- | ----- | --------------- |
| **A 全量直连 HIS** | 直接对接医院 HIS 与预约库              | 需院内网、厂商配合、安全评估 | 3–6 月 | ❌ 不推荐作为第一步      |
| **B 预约中台适配**   | 自建中台，对接医院统一预约平台/区域平台         | 需院方开放标准接口      | 1–2 月 | ✅ **终态**        |
| **C 导诊 + 转跳**  | 只做问诊导诊，最后一步出二维码让用户扫码在公众号完成挂号 | **零对接**        | 1–2 周 | ✅ **Demo 与冷启动** |

### 为什么必须先 C 后 B

1. **C 路径完全不依赖任何外部系统**，可以立刻演示、立刻上线跑数据。
2. 先用 C 验证"老人愿不愿意跟电视说话、导诊准不准"，这是**真正的产品风险**；接口对接是工程风险，晚点解决不致命。
3. C 阶段积累的**症状-科室映射数据**，正是 B 阶段最有价值的资产。

> 而且 C 路径在合规上最轻：不碰号源、不碰支付、不碰实名库，只出二维码。

## 5. 要跟「卫健」打通什么

| 能力             | 用途               | 必要性 | 落地路径                               |
| -------------- | ---------------- | --- | ---------------------------------- |
| **电子健康卡**      | 跨院唯一身份标识，替代各院就诊卡 | 高   | 走国家卫健委电子健康卡标准，由区域平台签发              |
| **实名核验**       | 确认"人证一致"         | 高   | 公安一所/运营商三要素核验                      |
| **区域全民健康信息平台** | 汇聚辖区内各院号源，统一查询   | 中高  | 深圳市/龙华区平台（需确认是否开放号源接口）             |
| **市预约诊疗服务平台**  | 统一号源池            | 中高  | 深圳有市级预约平台，**需确认龙华人民医院是否已接入及其接口形态** |
| 居民健康档案调阅       | 数字人可答"我上次检查结果"   | 低   | 需患者授权，合规成本高，二期再做                   |

**关键判断：卫健侧接口的价值是"统一"，但落地周期长、审批层级多。** 不要让项目卡在这里——先用医院单点接口（路径 B）跑通，卫健侧接口作为二期演进。

## 6. 要跟「医生」打通什么

需要说清楚一件事：**数字人不需要、也不应该直接对接医生个人。** 需要对接的是"医生的排班与号源"，这属于医院排班系统，不是医生本人。

| 需要        | 具体                      | 谁维护      | 说明                   |
| --------- | ----------------------- | -------- | -------------------- |
| 排班表       | 谁、哪天、哪个时段、看什么专病         | 门诊部/排班系统 | 数字人挂号的数据基础           |
| 号源类型      | 普通/专家/专病/特需，价格不同        | 门诊部      | 影响话术与支付              |
| **停诊与替诊** | 医生临时停诊                  | 排班系统     | 必须能推到电视端，否则老人白跑      |
| 加号规则      | 是否允许数字人申请加号             | 医务科      | 建议不开放，避免纠纷           |
| 接诊准备      | 挂号成功后给医生的提示（如"患者为独居老人"） | HIS 备注字段 | 增强，体现人文关怀            |
| 话术审核      | 导诊问法与科室推荐是否准确           | 医务科/门诊部  | **必须有人签字**，否则出问题无人担责 |

> 医生侧唯一真正需要"人"参与的环节是 **导诊话术与症状-科室映射的审核**。这个必须安排门诊部或医务科的人过一遍，不能由技术团队自己定。

## 8. 推荐架构：预约中台（Adapter 层）

```
数字人对话层
     ↓  统一意图：search / hold / confirm / cancel
【预约中台】  ← 自建，核心价值在这里
     ├─ 号源缓存（60s TTL，抗查询洪峰）
     ├─ 预占管理（锁号 120s，超时释放）
     ├─ 幂等与去重（防重复下单）
     ├─ 多院/多厂商 Adapter（HIS-A / HIS-B / 区域平台）
     └─ 降级（查不到 → 转二维码扫码挂号）
     ↓
医院统一预约平台 / 区域平台 / HIS
```

### 8.1 中台对外接口（对话层只认这 5 个）

```ts
POST /api/dept/match      { symptoms: string[] }        → { deptId, deptName, confidence }
GET  /api/schedule        ?deptId&dateFrom&dateTo       → Schedule[]
POST /api/hold            { scheduleId, patientId }     → { holdId, expireAt }
POST /api/confirm         { holdId, patientId }         → { orderNo, voucher }
POST /api/cancel          { orderNo }                   → { ok }
```

### 8.2 三个必须做对的机制

| 机制         | 做法                                  | 为什么                      |
| ---------- | ----------------------------------- | ------------------------ |
| **号源缓存**   | 查询走缓存（60s），只有 `hold` 打真实接口          | 电视端查询频次不可控，直连会打崩医院接口     |
| **预占而非直下** | 先 hold 再 confirm，中间留复述确认的时间         | 老人确认慢，直下会造成大量废单          |
| **幂等键**    | `patientId + scheduleId + 时间窗` 做唯一键 | 语音场景极易重复触发（老人重复说"挂""挂号"） |

## 9. 身份体系设计（落地级方案）

> 本章为 v0.2 重写章节，目标是把"身份认不出来"从思路变成**可实施、可验收**的方案。  
> 摘要版对比见 §15.1，本章给实现细节、数据模型、接口与异常处理。

### 9.1 先确认三个落地前提（不确认，方案都是空中楼阁）

| #  | 前提             | 要问什么                                                    | 拿不到会怎样          | 兜底                                             |
| -- | -------------- | ------------------------------------------------------- | --------------- | ---------------------------------------------- |
| P1 | 电视端能否持久化标识     | 机顶盒 WebView 的 localStorage / cookie 是否可靠、是否被系统清理、换盒子怎么办 | 每次开机都要重新绑定，体验崩塌 | 服务端下发 `deviceToken` 写 cookie + 服务端映射；绑定码方式不受影响 |
| P2 | 医院有无可用的手机端实名体系 | 公众号 / 小程序 / APP 是否已有"实名 + 就诊人管理"                        | 方案 A、B 都落不了地    | 降级到方案 C（客服代绑 / 卡号核验）                           |
| P3 | 医院能否提供就诊人查询接口  | 按"姓名 + 卡号"或"姓名 + 出生年月"能否查到 patientId                    | 电视端无法做任何身份核验    | 降级到方案 C3（电视只做展示，全流程手机托管）                       |

> **建议本周就去问清这三点。** 只要 P2 成立，方案 A+B 就能立刻开工；P2 不成立，整个项目的形态要改（变成"电视叫号机 + 提醒器"）。

### 9.2 方案 A：扫码绑定（自助主流）

#### 流程

```
电视端                              服务端                       手机端
  │  ①显示二维码(短码)               │                             │
  │──────────────────────────────→  │ 生成 bindSession            │
  │  ②每 2s 轮询 status             │                             │
  │──────────────────────────────→  │ ←──③扫码打开公众号/H5 ──────│
  │  ④状态变 SCANNED，显示"已扫描"   │                             │
  │←──────────────────────────────  │ ←──⑤选择就诊人+点确认 ──────│
  │  ⑥状态变 CONFIRMED              │                             │
  │←──────────────────────────────  │ 建立 device↔patient 绑定     │
  │  ⑦语音播报"绑定成功，以后不用再绑"│                             │
```

#### 二维码规范（这些细节决定老人能不能扫成功）

| 项    | 要求                                             | 原因               |
| ---- | ---------------------------------------------- | ---------------- |
| 尺寸   | 电视上 ≥ **240×240 px**（55 寸 / 3 米观看）             | 小了手机对焦不上         |
| 内容   | **短码 URL**（如 `https://hosp.cn/b/7K2M9X`），不用长参数 | 参数过长二维码过密，老手机扫不出 |
| 有效期  | 120 秒，倒计时环显示                                   | 明确预期             |
| 刷新   | 过期自动换码，**位置不动**                                | 位置跳动老人会找不到       |
| 容错等级 | QR 容错 M 级                                      | 兼顾密度与容错          |
| 辅助   | 二维码下方大字显示 6 位数字码（同屏双通道，见 §9.5）                 | 老人自己扫不了可念给子女     |

#### 三个必须做的状态提示

| 状态          | 电视端表现                       | 为什么必须               |
| ----------- | --------------------------- | ------------------- |
| `PENDING`   | "请用手机微信扫这个码"                | 明确下一步               |
| `SCANNED`   | **"已扫描，请在手机上点确认"** + 手机图标动效 | 最常见的卡点：老人扫完不知道还要点确认 |
| `CONFIRMED` | 全屏打勾 + 语音"绑定成功，以后不用再绑了"     | 建立信任，避免重复操作         |

#### 落地依赖

| 依赖                 | 提供方            | 工作量    | 备注                    |
| ------------------ | -------------- | ------ | --------------------- |
| 公众号/H5 绑定页（扫码后落地页） | 医院信息科 / 公众号运营方 | 3–5 人日 | 若已有实名体系，只需加一个"绑定设备"动作 |
| 绑定状态轮询接口           | 自建             | 0.5 人日 | —                     |

**成本**：1 周（含联调）。**适合**：有智能手机、会用微信的老人（占比约 40–50%）。

### 9.3 方案 B：家庭账户 + 6 位绑定码（老人主路径）

#### 核心思路

**不要求老人在电视上做任何"认证动作"**，而是让子女在自己手机上完成绑定。老人只需要把电视上的 6 个数字念给子女听。

#### 流程

```
电视端：大字显示  4 8 2 9 1 7   「请让家人帮您绑定」
   ↓ 老人打电话 / 子女在旁边
子女手机（已实名）：公众号 → 我的 → 添加家庭成员 → 输入 482917
   ↓
选择要绑定的就诊人（父亲/母亲/自己）→ 确认
   ↓
电视端立刻切换："您好，张秀兰阿姨" + 语音播报
```

#### 数据模型

```sql
-- 家庭账户（以手机号为锚，一个家庭一个）
family_account(
  id, owner_phone, owner_name, created_at, status
)

-- 家庭成员 / 就诊人（可多个）
family_member(
  id, family_id, patient_id, name, relation,     -- 父/母/本人/配偶
  is_default, sort_order, created_at
)

-- 设备绑定（一台电视一条，支持多设备）
device(
  id, device_token, iptv_account, family_id,
  bound_at, last_active_at, status               -- active/unbound
)

-- 绑定码（一次性，5 分钟有效）
bind_code(
  code, family_id, expire_at, used_at, status
)

-- 操作日志（合规与追责必需）
bind_log(id, device_id, family_id, action, operator_phone, ip, created_at)
```

#### 关键实现细节

| 细节        | 做法                                   | 原因            |
| --------- | ------------------------------------ | ------------- |
| 码字符集      | 排除 `0/O/1/I/8/B`，只用 2–9 与 A–F 中的清晰字符 | 老人念错、听错是高频事故  |
| 有效期       | 5 分钟，一次性使用                           | 防撞码           |
| 一设备一家庭    | 一台电视只归属一个 `family_account`           | 避免家庭内部串号      |
| 一家庭多设备    | 客厅 + 卧室可各绑一台，共享就诊人                   | 真实家庭结构        |
| **默认就诊人** | 绑定后记住 `last_active_member`，开机自动用     | 老人不需要每次"选我是谁" |
| 换人        | 说"换成我老伴" → 弹成员列表（≤3 个，大字）            | 一句话完成，不用扫第二次  |
| 解绑        | 手机端操作；电视端**长按返回键 5 秒**（防误触）          | 双向入口          |

#### 落地依赖

| 依赖          | 提供方            | 工作量                           |
| ----------- | -------------- | ----------------------------- |
| 公众号"家庭成员"功能 | 医院信息科 / 公众号运营方 | 3–5 人日（若已有家庭就诊人管理，仅加"设备绑定"入口） |
| 家庭账户与设备表    | 自建             | 3 人日                          |

**成本**：1.5–2 周。**适合**：老人场景主路径（子女代劳是真实刚需，不是补充）。

### 9.4 方案 C：兜底通道（无手机 / 不会用手机）

不追求覆盖率，只追求"没有一个人被挡在门外"。

#### C1 客服代绑（**成本最低、100% 可落地、老人最认**）

| 项       | 内容                                                                                           |
| ------- | -------------------------------------------------------------------------------------------- |
| 做法      | 老人按遥控器"帮助/客服"键，或说"找个人帮我" → 转医院客服 → 客服核验身份（姓名 + 出生年月 + 手机号后 4 位）→ 后台把设备绑定到该患者 → 电视端 10 秒内自动生效 |
| 优点      | 复用医院现有呼叫中心，几乎零开发；老人对"有人接电话"接受度最高；全程留痕可追责                                                     |
| 缺点      | 占客服人力；高峰期排队                                                                                  |
| 依赖      | 客服中心愿意承接 + 一个代绑后台页面                                                                          |
| 成本 / 工期 | 低 / 3–5 人日（含后台页）                                                                             |
| 建议      | **必做**，作为 A、B 都失败时的最后一层                                                                      |

#### C2 就诊卡后 4 位 + 出生年月（纯电视端核验）

| 项       | 内容                                                        |
| ------- | --------------------------------------------------------- |
| 做法      | 数字人问两个问题，遥控器数字键输入 → 匹配 `patientId` → 仅建立**当次会话**身份，不做长期绑定 |
| 优点      | 不依赖手机与公众号；纯电视闭环                                           |
| 缺点      | 老人念数字/按数字键困难；安全等级低（家人之间无隔离）；需院内患者库查询接口（前提 P3）             |
| 成本 / 工期 | 低 / 3 天                                                   |
| 建议      | **仅作临时查询用**，不用于挂号下单                                       |

#### C3 手机全托管（电视只做展示与提醒）

| 项       | 内容                                                    |
| ------- | ----------------------------------------------------- |
| 做法      | 电视只显示二维码跳转公众号挂号页，全部流程在手机完成；电视端只负责"预约提醒 + 大字凭证 + 就诊导航" |
| 优点      | **零风险、零对接**，最容易过审；上线最快                                |
| 缺点      | 数字人价值最弱（退化为叫号机+提醒器）；项目叙事不亮                            |
| 成本 / 工期 | 极低 / 2 天                                              |
| 建议      | **作为 P2/P3 前提都不满足时的退路**，也是 P0 Demo 的降级演示路径            |

### 9.5 组合策略：三段式身份漏斗（推荐）

**方案不是三选一，而是同屏并列 + 分层兜底。**

```
新用户首次开机
   │
   ├─ 电视同屏显示：【二维码】 + 【6 位数字码】 + 【"找客服帮我"按钮】
   │
   ├─ ① 老人自己有手机、会扫码 ──────────→ 方案 A（自助绑定）
   ├─ ② 老人在子女身边 / 打电话念数字 ────→ 方案 B（子女代绑）  ← 真实占比最高
   ├─ ③ 都不会 / 两次失败 ───────────────→ 方案 C1（客服代绑）
   │
   └─ 绑定成功 → 永久免认
        │
        ├─ 日常：自动用 last_active_member，换人一句话
        ├─ 异常：设备重置 / 换盒子 / 解绑 → 回到第①层重来
        └─ 兜底：任何环节说"找个人帮我" → 客服
```


**这个漏斗最关键的一条设计：二维码和 6 位码必须同屏显示，不做二选一。**

原因很实在——老人独处时不会扫码，但**会念数字给电话那头的子女听**。这一条能覆盖 90% 以上真实家庭场景，且实现成本几乎为零（同一个 `bind_code` 既编码成二维码，也大字显示）。

#### 三层覆盖率预估

| 层 | 覆盖人群 | 预估占比 | 成本 |
|---|---|---|---|
| A 扫码 | 会用微信的老人 | 40–50% | 1 周 |
| B 代绑 | 子女协助的老人 | 40–50%（与 A 有重叠） | 1.5–2 周 |
| C1 客服 | 独居、无手机、认知障碍 | 5–10% | 3–5 天 |
| C2 卡号 | 临时查询 | 不用于挂号 | 3 天 |

### 9.8 异常矩阵（这些必须提前想好，否则上线必炸）

| 异常 | 用户看到什么 | 处理 |
|---|---|---|
| 二维码过期 | "码过期了，我帮您换个新的" + 自动刷新 | 自动，无需用户操作 |
| 扫了码但没点确认 | "已扫描，请在手机上点一下确认"（持续提示 30s） | 主动催促，这是最高频卡点 |
| 扫码后手机端报错 | "手机上没成功，要不我帮您叫客服？" | 一键转 C1 |
| 家庭成员 > 3 人 | 列表分页 / "更多" 入口 | 老人场景一般 ≤ 3，超出走手机端管理 |
| 机顶盒重置 / 换盒子 | 回到首次绑定流程 | `deviceToken` 失效需重新绑 |
| 一个家庭两台电视 | 两台都绑到同一 `family_account`，共享就诊人 | 支持多设备 |
| 电视被客人使用 | 开机显示"当前就诊人：张秀兰"，可一键"不是我" | 隐私提示 + 切回待机 |
| 就诊人改名 / 换卡 | 手机端更新后，电视端下次开机同步 | 不做实时推送 |
| 绑定后台挂了 | "暂时连不上，请稍后再试" + 保留码可重试 | 降级不白屏 |

### 9.9 授权与隐私（合规硬要求）

- **明示同意**：首次绑定必须在电视端用**大字 + 语音播报**告知"将把您的就诊信息关联到这台电视"，不能只放一行小字链接。
- **最小必要**：只取挂号必需字段（姓名、性别、出生年月、就诊卡号），不取身份证全码、不取病史。
- **电视端展示限制**：不显示身份证号全码、不显示诊断结论、不显示检查明细（家里可能有客人）。
- **可撤回**：手机端提供解绑入口；电视端长按返回键 5 秒亦可。
- **日志留存**：绑定/解绑/切换就诊人的操作日志留存 ≥ 6 个月（等保要求）。
- **代绑责任**：客服代绑必须记录 `operatorId`，出纠纷可追溯。

| # | 依赖 | 提供方 | 具体内容 | 需要时间 | 拿不到的替代 |
|---|---|---|---|---|---|
| 1 | 公众号实名 + 就诊人管理 | 医院信息科 / 公众号运营 | 已有则加"绑定设备"动作 | 3–5 人日 | 方案 C3 |
| 2 | 就诊人查询接口 | HIS 厂商 | 姓名+卡号 → patientId | 5 人日 | 方案 C3 |
| 3 | 客服代绑后台 | 医院客服中心 | 一个代绑页面 + 权限 | 3–5 人日 | 方案 C2 |
| 4 | IPTV 设备标识 | 播控方 / 运营商 | MAC 或账号，或允许自生成 token | **不确定，需尽早问** | 自生成 `deviceToken` |
| 5 | 明示同意文案 | 医院法务 / 医务科 | 法律文本 | 3 天 | 不可替代，必须院方出 |

### 9.11 多成员就诊人选择（方案 A / B 通用）

> 绑定完成后，家庭账户里可能有多位就诊人（本人、老伴、子女、孙辈）。本节回答：**挂号时"给谁挂"这件事怎么处理。**

#### 9.11.1 核心原则：默认隐式，例外显式

| 层级 | 机制 | 覆盖率 | 老人要做什么 |
|---|---|---|---|
| **L0 隐式默认** | 全程不出现选择器，自动用"当前就诊人" | ~70% | **什么都不做** |
| **L1 语音切换** | 一句话："给我老伴挂" | ~25% | 说一句话 |
| **L2 显式选择器** | 遥控器点右上角 / 说"换个人" | ~5% | 按方向键选 |

**硬规则：绝不在流程开头弹"请选择就诊人"列表。**

原因很实在——每次挂号都先选人，等于把最常见的"给自己挂"变成了多步操作。老人本来就怕点错，一上来给 4 个选项，直接就退了。

#### 9.11.2 "当前就诊人"的取值优先级

| 优先级 | 规则 | 说明 |
|---|---|---|
| 1 | 本次会话内已切换过的成员 | 会话内保持不变，不反复问 |
| 2 | 该设备 `last_active_member` | 上次用的是谁，这次还是谁 |
| 3 | 家庭账户 `is_default` | 初始默认 |
| 4 | 账户下只有 1 位成员 | 直接用，连显示都省 |
| 5 | 都没有 | 触发绑定流程 |

**超时回落：5 分钟无操作 → 回落到 `last_active_member`。**

这一条防的是真实场景：子女白天用电视给父母挂完号，晚上老人自己开机，如果停在子女身上，老人一开口就把号挂到子女名下。

#### 9.11.3 电视端常驻标识

屏幕右上角常驻一条窄条：

```
┌────────────────────────┐
│ 当前：张秀兰（本人）  ▾ │
└────────────────────────┘
```

| 项 | 规范 |
|---|---|
| 高度 | 60 px，半透明 70% 底，不抢数字人视觉 |
| 字号 | 32 px，不放大也不缩小 |
| 交互 | 焦点移到该条按【确认】→ 弹成员选择器 |
| 显示时机 | 常驻（老人几乎不会动它，但子女用时会找它） |

#### 9.11.4 成员选择器 UI 规范

| 项 | 规范 |
|---|---|
| 布局 | 2×2 网格（一屏最多 4 人，第 5 人起放「更多 ▸」，上限 6 人） |
| 卡片尺寸 | 320×180 px |
| 卡片内容 | 插画头像（直径 96px）+ 称呼大字 48px「老伴 李国强」+ 关系小字 32px |
| 焦点 | 6 px 高对比描边 + 轻微放大 1.05，无其他动效 |
| 首焦位置 | 停在上次使用的成员上，不从头开始 |
| 右下角 | 「添加家人」→ 出 6 位码 / 二维码，**电视端不能直接新增成员** |
| 选择后 | 语音确认"好的，给李国强挂号"，避免误选不自知 |

#### 9.11.5 语音切换的说法与解析

| 老人说法 | 解析 | 无/多匹配时 |
|---|---|---|
| "给我自己挂" / "我自己的" | `relation = 本人` | — |
| "给我老伴挂" / "给老头子" | `relation = 配偶` | 若无配偶 → 弹选择器 |
| "给我妈挂" / "给老娘" | `relation = 母` | 若无 → 弹选择器，**不猜** |
| "给孙子挂" | `relation = 孙` | 若无 → 弹选择器 |
| "给张秀兰挂" | 姓名模糊匹配 | 重名 → 追问关系 |
| 关系有多个匹配（父母都在） | 弹选择器 | — |

**关键：宁可弹选择器，也不要猜。** 挂错人之后要取消、要重挂、要跟医院沟通，代价远大于多按一次方向键。

#### 9.11.6 切换后必须重新校验号源适用性（最容易被忽略的坑）

切换就诊人后，**之前选中的号源要立即重新校验**，否则会出现"给老伴挂了妇科"这种荒唐事：

| 校验规则 | 处理 |
|---|---|
| 妇科 / 产科 | 男性成员不可选，号源直接过滤 |
| 儿科 | 年龄 > 14 岁不可选 |
| 部分专家号 | 限初诊 / 限复诊 |
| 医保类型 | 自费号与医保号源不同，需按成员医保状态过滤 |
| 儿童疫苗 / 孕产 | 按性别与年龄段过滤 |

不通过时的话术：

> "这个号是妇科的，李国强挂不了。我帮您看看别的科，好吗？"

然后自动重查，**不要把用户扔回首页**。

#### 9.11.7 确认卡片（防挂错人的最后一道闸）

```
┌──────────────────────────────────┐
│  ① 就诊人   张秀兰（您本人）        │
│    科  室   心血管内科             │
│    医  生   王医生 · 副主任医师     │
│    时  间   11月8日 周六 上午       │
│                                  │
│      说"对"    或    按【确认】     │
└──────────────────────────────────┘
```

| 规范 | 要求 |
|---|---|
| 就诊人位置 | **第一行**，字号最大（56 px），带序号 ① |
| 代他人时 | 显示「（代 李国强 挂号）」，不允许只显示姓名 |
| 语音复述 | 必须念全名且放慢："给、李、国、强、挂、心、内、科，对、吗？" |
| 下单成功页 | 再显示一次就诊人姓名 + 提供 30 分钟内自助取消入口 |

> 就诊人放在第一行、字号最大，是因为它是**唯一一个错了会导致实际损失的字段**——科室错了还能重挂，人错了就是给别人占了号、自己没看上。

#### 9.11.8 代挂的合规与追溯

| 项 | 要求 |
|---|---|
| 数据记录 | `appointment` 记录 `patient_id` + `booked_by_member_id` + `channel`(tv/mobile/agent) + `is_proxy` |
| 授权范围 | 家庭账户内切换视为已授权（绑定时的一次性明示同意覆盖全家人） |
| 跨家庭 | **不允许**，任何跨账户取号都会被拒绝 |
| 日志 | 代挂操作单独标记 `is_proxy=1`，留存 ≥ 6 个月，便于纠纷追溯 |

#### 9.11.9 数据模型增补

```sql
ALTER TABLE family_member ADD COLUMN relation VARCHAR(16);   -- 本人/配偶/父/母/子/女/孙
ALTER TABLE family_member ADD COLUMN nickname VARCHAR(32);   -- 老伴/老头子，用于语音称呼
ALTER TABLE family_member ADD COLUMN avatar_url VARCHAR(255);
ALTER TABLE family_member ADD COLUMN last_used_at TIMESTAMP; -- 驱动排序与首焦

ALTER TABLE device ADD COLUMN last_active_member_id BIGINT;

CREATE TABLE appointment(
  id                BIGINT PRIMARY KEY,
  patient_id        BIGINT NOT NULL,        -- 给谁挂
  booked_by_member_id BIGINT NOT NULL,      -- 谁下的单
  is_proxy          TINYINT DEFAULT 0,      -- 是否代他人
  dept_id           BIGINT,
  doctor_id         BIGINT,
  schedule_id       BIGINT,
  channel           VARCHAR(16),            -- tv / mobile / agent
  status            VARCHAR(16),
  created_at        TIMESTAMP
);
```

#### 9.11.10 并发冲突处理

| 场景 | 处理 |
|---|---|
| 手机端与电视端同时对同一就诊人下单 | 幂等键 `patient_id + schedule_id + 时间窗`，第二次直接返回已有订单 |
| 家庭成员在两台电视各自切换 | 各自独立会话，互不干扰（`device` 维度隔离） |

## 15. 三大难点的解决思路对比（决策用）

> 使用方法：每个难点下 3 条思路，可单选也可组合。每条都标了「依赖 / 成本 / 工期 / 建议阶段」，最后一节给出推荐组合。

### 15.1 难点① 身份认不出来

> **本节为决策摘要。v0.2 已在第 9 章给出落地级方案（数据模型、接口、状态机、异常矩阵、验收标准），实施请以第 9 章为准。**

**问题本质**：电视端没有输入法、没有实名信息，IPTV 账号只对应宽带，不对应患者。

#### 方案 ①-A：扫码绑定（电视出码 → 手机确认）

| 项 | 内容 |
|---|---|
| 做法 | 电视显示二维码 → 用户用手机微信/医院公众号扫码 → 手机端完成实名与就诊人绑定 → 电视端自动登录并显示"您好，张阿姨" |
| 优点 | 唯一顺滑的首次绑定方式；安全等级最高（实名在手机端完成）；可复用医院已有公众号实名体系，无需新建 |
| 缺点 | 老人独自在家不会扫；需手机与电视同时在手；二维码有效期需管理（建议 120s） |
| 依赖 | 医院公众号/小程序已有实名与就诊人管理能力 |
| 成本 / 工期 | 中 / 1 周（含二维码状态轮询、超时刷新） |
| 建议阶段 | **P0 演示（浮层模拟）+ P1 上线（首次绑定必走）** |
| 关键细节 | 二维码要**大字 + 高对比 + 带倒计时**；扫描成功后电视端立刻语音播报"绑定成功"，给老人确认感 |

#### 方案 ①-B：家属远程代绑 + 长期免认（家庭账户）

| 项 | 内容 |
|---|---|
| 做法 | 子女在医院公众号把父母添加为"家庭成员"，并输入电视上显示的 6 位绑定码完成设备授权；此后电视端永久免认，自动使用"默认就诊人" |
| 优点 | **老人零操作**，一次绑定长期有效；最符合真实家庭结构（子女本来就是代挂主力）；可支撑一个账号下多个就诊人 |
| 缺点 | 需建设家庭账户模型 + 授权管理 + 解绑入口；首次仍需子女参与；涉及健康信息，需明示同意 |
| 依赖 | 医院账号体系支持"一人多就诊人" |
| 成本 / 工期 | 中高 / 1.5–2 周 |
| 建议阶段 | **P1 主路径（老人场景核心）** |
| 关键细节 | 老人不需要记住"我是谁"——系统自动用上次就诊人；换人只需说"换成我老伴" |

#### 方案 ①-C：就诊卡后 4 位 + 姓名语音核验（纯电视闭环）

| 项 | 内容 |
|---|---|
| 做法 | 数字人问"请问就诊卡后四位是多少"，用户语音或遥控器数字键输入，与院内库匹配后建立会话身份 |
| 优点 | 完全不依赖手机；纯电视端闭环；实现最简单 |
| 缺点 | 老人念数字（尤其方言）识别率低；后 4 位不唯一，需二次确认；同一家庭内无隐私隔离（家人互相能看到） |
| 依赖 | 无（只需院内患者库查询） |
| 成本 / 工期 | 低 / 3 天 |
| 建议阶段 | **兜底通道，不作为主路径** |
| 关键细节 | 必须给数字键输入备选；连续 2 次失败直接转 ①-A 扫码 |

#### 补充：无感识别（用运营商宽带账号预绑定）—— 不建议

运营商把宽带账号与手机号关联，医院侧预存映射，电视开机即识别。理论上体验最好，但**需跨机构开放账号数据，隐私合规成本极高，且宽带户主 ≠ 患者**（老人家里宽带常是子女办的）。**建议不做。**

### 15.2 难点② 号源实时变动，确认耗时导致被抢

**问题本质**：号源秒级变化，而"语音问答 + 老人确认"天然慢，中间几十秒足以被抢走。

#### 方案 ②-A：预占锁号（Hold → Confirm 两段式）

| 项 | 内容 |
|---|---|
| 做法 | 查到号后先调 hold 接口锁定 90–120s，用户有充足时间听复述、确认；确认后转正式订单；超时自动释放 |
| 优点 | **根本性解决**，把不确定性挡在用户感知之外；体验从"赌运气"变成"确定" |
| 缺点 | 强依赖预约平台提供 hold 接口（多数医院不提供）；锁号期间占用号源，需限流防滥用 |
| 依赖 | 医院统一预约平台/号源池支持预占 |
| 成本 / 工期 | 中 / 1 周（不含院方改造）+ 院方协调 |
| 建议阶段 | **P1 终态方案** |
| 关键细节 | 锁号到期前 20s 主动语音提示"还有 20 秒，需要帮您确认吗"；同一患者同科室只保留 1 个有效 hold |

#### 方案 ②-B：压缩确认路径 + 并行预取（不依赖院方改造）

| 项 | 内容 |
|---|---|
| 做法 | ① 把"选科室→选医生→选日期→选时段→确认"压成**一次只给 3 个候选时段**，说"第一个"即下单；② ASR 的 partial 一出现"挂号"，后台就并行预查号源；③ 确认环节从"复述 4 项"减为"复述 2 项（科室+时间）" |
| 优点 | **不依赖任何院方接口改造**，纯前端与编排优化；把 60 秒压到 10 秒内；可立即在 Demo 中实现 |
| 缺点 | 不消除失败可能，只把概率从"高"降到"低"；候选只给 3 个会让可选范围变窄 |
| 依赖 | 无 |
| 成本 / 工期 | 低 / 3 天 |
| 建议阶段 | **P0 必做，P1 与 ②-A 叠加** |
| 关键细节 | 老人面对 3 个选项比面对 20 个号源更快做决定；顺序按"最近时间优先"排，不按价格 |

#### 方案 ②-C：失败降级（二维码接力 + 候补队列）

| 项 | 内容 |
|---|---|
| 做法 | 占号失败时不显示"失败"，而是：出二维码"扫这个码，手机上还有 1 个号"；或进候补队列，有人退号自动抢并推送提醒 |
| 优点 | 不把失败暴露成失败，转成另一条路；候补队列还能提升号源利用率 |
| 缺点 | 体验割裂（电视→手机）；候补成功需即时通知，落地依赖短信/推送 |
| 依赖 | 短信或公众号模板消息 |
| 成本 / 工期 | 低 / 2–3 天 |
| 建议阶段 | **P0 就要有（至少二维码降级），P2 补候补队列** |
| 关键细节 | 话术不能说"没号了"，要说"这个号刚被占用了，我帮您换个方式" |

#### 补充：数字人专属号源池（自建弹性池）—— P2 商务争取

与医院协商，每医生每日预留 1–2 个"线上服务号"放入自有池，电视端直接扣减，彻底规避抢号。

| 项 | 内容 |
|---|---|
| 优点 | 体验最稳，彻底解决；也是项目可量化的运营抓手 |
| 缺点 | 需院方政策支持；预约不来看会造成号源浪费（需配合爽约管理） |
| 成本 | 高（商务协调为主，非技术） |
| 建议阶段 | P2 争取，不作为前置条件 |

### 15.3 难点③ 老人不会操作，必须有人代劳

**问题本质**：老人说不清科室、记不住信息、怕点错，任何需要"多步操作"的设计都会失败。

#### 方案 ③-A：家庭账户 + 远程代挂（子女手机端下单）

| 项 | 内容 |
|---|---|
| 做法 | 子女在自己手机上通过公众号选号下单，电视端只承担"查看预约 / 就诊提醒 / 大字号凭证展示" |
| 优点 | 最符合现实（子女本就是代挂主力）；零学习成本；电视端职责简单、不易出错 |
| 缺点 | 数字人在此路径上退化为"查询终端"，价值被削弱；项目叙事上不够亮眼 |
| 依赖 | 医院公众号已有代挂号能力 |
| 成本 / 工期 | 中 / 1 周 |
| 建议阶段 | **P1 并行主路径** |
| 关键细节 | 电视端要能把"子女刚帮你挂了周五上午心内科"用大字+语音播出来，这才是电视的价值 |

#### 方案 ③-B：电视端"一句话挂号"极简流（数字人代办）

| 项 | 内容 |
|---|---|
| 做法 | 老人只说"我要看心脏"，数字人负责科室匹配、医生推荐、时段给 3 选 1、复述确认、下单。全程老人只需回答 **3 次"是/不是"**，任何一步 15s 无响应自动追问，2 次失败转人工 |
| 优点 | **数字人价值最大化**，真正的适老化；差异化最强，评委最买账 |
| 缺点 | 强依赖 ASR 准确率与导诊准确率；推荐错科室会引发投诉，责任归属需医务科背书 |
| 依赖 | 症状→科室知识库（需医务科审核签字）+ 高准确率 ASR |
| 成本 / 工期 | 中 / 2 周（知识库需院方配合） |
| 建议阶段 | **P0 演示主角 + P1 主路径** |
| 关键细节 | ① 全程不超过 3 次确认；② 每次确认都复述"科室+时间"两项；③ 说"我不确定"就降级给 3 个科室让用户选，不硬猜 |

#### 方案 ③-C：远程协助（子女手机接管电视会话）

| 项 | 内容 |
|---|---|
| 做法 | 老人卡住时，子女手机端可"接管"当前电视会话，看到电视上的界面并代为操作，操作结果实时反映到电视 |
| 优点 | 精准解决"卡在某一步"；技术上也是很强的演示点 |
| 缺点 | 会话同步实现复杂；隐私与授权设计难；老人可能不理解"我的电视被人动了" |
| 依赖 | 双端会话状态同步 + 授权 |
| 成本 / 工期 | 高 / 3 周以上 |
| 建议阶段 | **P3，暂不做** |

#### 方案 ③-D：一键转人工（安全网）

| 项 | 内容 |
|---|---|
| 做法 | 说"找个人帮我"或连续 2 次失败 → 转医院客服，客服端能看到完整会话上下文（已问过什么、卡在哪） |
| 优点 | 最可靠的安全网；成本可控；对老人心理是"有退路" |
| 缺点 | 需客服排班与工单系统；高峰期排队 |
| 依赖 | 医院客服中心/呼叫中心 |
| 成本 / 工期 | 低–中 / 3–5 天（对接既有客服系统则更低） |
| 建议阶段 | **P1 必须有（可先做"留言回呼"轻量版）** |
| 关键细节 | 转人工时必须把上下文一并递过去，不能让老人从头再说一遍 |

### 15.4 推荐组合

| 阶段 | 身份（①） | 号源（②） | 代劳（③） | 组合效果 |
|---|---|---|---|---|

### 15.5 我的建议（如果只能选三条）

| 难点 | 单选建议 | 理由 |
|---|---|---|
| ① 身份 | **①-B 家庭账户** | 老人零操作是唯一能提升真实使用率的方案，扫码只是它的入口 |
| ② 号源 | **②-B 压缩确认 + 并行预取** | 不依赖院方改造就能把 60s 压到 10s，投入产出比最高 |
| ③ 代劳 | **③-B 一句话挂号** | 这是整个项目唯一"别人接不走"的价值，也是演示最打动人的部分 |

> 注意 ②-B 和 ③-B 是相互加强的：确认环节越少，②的抢号风险越小。**两个方案一起做，比单独做任何一个效果都好。**

## 16. 一句话总结

**对外要的只有三样：号源、排班、身份。** 其余七项（导诊知识库、家庭账户、槽位引擎、预约中台、凭证、提醒、形象话术）全部自建——**这些才是这个项目的差异化，也是别人接不走的部分。**
